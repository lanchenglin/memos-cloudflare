# ywdj 运维登记：第一版需求与实现约定

## 1. 定位和边界

从 `main` 的 `0383b3ee90acdda3b60c7b011ba0dd668ad62fbe` 创建独立长期分支 `ywdj`。它是轻量运维事件台账，不是原个人随手记的权限开关，也不是工单审批平台。

核心：当天登记、提交锁定、追加留痕、按日查询、沿事故编号追溯。

本次只约束应用侧。数据库管理员权限、Cloudflare 控制台权限、数据库级防篡改、R2 保留锁和合规认证不在范围内。新建业务表、外键和唯一约束用于数据一致性，不是对数据库管理员的权限设计。

第一版采用**单实例、单团队**：所有启用的登录成员可查看全部正式登记及其附件；未登录不能读取。没有部门、租户、项目级隔离。应部署到独立站点，不与个人笔记共享生产数据库或 R2。

## 2. 明确的权限规则

| 操作 | 普通成员 | 管理员 |
|---|---|---|
| 新增当天初报、告警、操作 | 允许 | 允许 |
| 修改尚未提交的本机草稿 | 允许 | 允许 |
| 修改、覆盖、归档隐藏、删除正式记录 | 禁止 | 同样禁止 |
| 覆盖、解绑、删除正式记录附件 | 禁止 | 同样禁止 |
| 为历史事故追加今天的处置、恢复、复盘 | 允许 | 允许 |
| 追加更正说明，原文不变 | 允许 | 允许 |
| 新增作废说明、标记目标记录 | 禁止，使用更正说明 | 允许，必须注明对象和原因 |
| 查询、导出团队正式记录 | 允许 | 允许 |
| 查看系统操作审计 | 禁止 | 允许 |
| 新建、停用、启用账号 | 禁止 | 允许 |
| 删除账号及级联记录 | 禁止 | 同样禁止，用停用代替 |

不能停用或降级当前登录管理员，不能使启用的管理员数量降为零。权限、账号状态和密码变化会撤销该用户旧会话令牌。登记人保留稳定用户 ID 和提交时的用户名、显示名快照，不随改名重写历史。

## 3. 时间、跨天与更正

`recordedAt` 是服务器生成的真实登记时间；`recordedDate` 是该时间按业务时区换算出的日期。客户端不允许传入登记时间、登记人、创建时间或可见性字段。时间存 UTC 毫秒，业务日期和时区随记录保存。

业务时区由部署配置 `AUDIT_TIMEZONE` 决定，默认 `Asia/Shanghai`，不是访问者的电脑时区。已有正式数据后不应随意切换业务时区；配置错误应报错，不静默回退。

`occurredAt` 是事件实际发生时间：可以留空（采用服务器接收提交时刻），或填写业务时区当天已经发生的时刻。不能填写昨天、明天、晚于服务器当前时间的时刻。第一版不提供历史补录通道，管理员也不能倒填。

跨天例子：9 月 30 日登记告警，10 月 1 日点击原记录“追加进展”，提交今天的恢复说明。它属于 10 月 1 日的新记录，但 `incidentId` 指向原事故。按 9 月 30 日查能找到初报，打开完整事故链能看到两天全部记录及各自真实登记时间。

更正必须新增一条 `CORRECTION`，指定同一事故内的原记录编号 `targetId`，正文说明错误和更正结论。原记录不覆盖。作废同理，新增 `VOID`，原文和证据继续显示；“作废”不是物理删除。

前端在提交前重新取得服务器日期。填写了具体时分的草稿应绑定填写时的业务日期，跨天后要求重新选择，不把昨天的时分悄悄解释为今天。

## 4. 记录内容与界面

类型：告警 `ALERT`、事故初报 `INCIDENT`、处置/操作 `ACTION`、恢复确认 `RECOVERY`、复盘 `REVIEW`、更正 `CORRECTION`、作废 `VOID`。

首次登记允许告警、事故初报或操作；其余类型必须关联已有事项。新进展沿用原事项所属系统，不能串到不同事故的更正对象。

必填内容：类型、标题、所属系统、严重程度和正文。初报只需要描述现象、影响和已掌握证据，不要求填写尚未确认的根因。标题最多 160 字符，系统名 120，正文 32768，每条最多 20 个图片/PDF。默认单附件 10 MiB，可配置 1–20 MiB。原始文本日志先粘贴正文；没有自动解析告警、OCR 或 AI 根因分析。

主界面 `/audit` 有登记台账、账号设置、管理员操作审计。旧个人笔记页面不再作为可写入口。

查询支持登记日期/发生日期、全部日期、记录类型、严重程度、系统精确值、登记用户名精确值、中文关键词、事故编号及附件文件名。按真实登记先后排序。完整事故链默认取消日期及其他局部筛选，显示跨天全链，分页继续加载而不是截断。

## 5. 提交可靠性和附件

草稿存在当前浏览器，按稳定账号 ID 隔离；不是云草稿。正式提交前二次确认。请求编号和完整待提交请求先持久化，再向后端发送。

每个提交使用 `requestId`。后端以 `(actor_id, request_id)` 唯一去重，并核对请求内容摘要。同一请求重试返回原记录；编号相同但内容不同返回 409。重试查重先于当天校验，所以午夜后重试昨天已成功的提交不会新建第二条。

网络错误或不确定的服务端响应发生时保留原请求并暂时锁住草稿编辑，提供“原样重试确认提交”；刷新浏览器后继续同一请求，而不是重新生成编号。

附件先进入仅上传者可访问的暂存区。正式提交时记录、证据关联、成功审计日志在一个 D1 batch 事务内写入。附件不存在、不属于上传者或已被其他记录使用，整批回滚，不留下半条记录。唯一关联约束和外键覆盖并发争抢附件的情况。

每次实际 R2 上传使用新对象 key，重试不会覆盖已有文件。保存文件字节数、识别类型和 SHA-256。只允许移除尚未正式绑定的本人草稿附件；已提交证据无应用删除入口。上传失败补偿和草稿附件删除失败使用持久删除补偿队列。

暂存区没有自动过期清理策略。放弃草稿前应移除附件；后续可增加有明确保留期的暂存清理，不能将正式证据纳入清理。

## 6. 防止旧入口绕过

生产 `backend/src/index.ts` 固定使用 `createApp(true)`，无用户可改的模式开关。旧 MemoService、AttachmentService、个人上传/导出、旧附件访问和 DeleteUser 在审计版统一拒绝；不能通过编辑、批量删除、改时间、附件重绑定、分享、删除用户级联等入口改变台账。

正式记录采用独立 `audit_record`、`audit_upload`、`audit_evidence`、`audit_log` 表，不把个人笔记悄悄转换成审计证据。迁移只增加表和索引并更新产品标题/关闭注册，不删除原数据。

`tests/fixtures/personal-worker.ts` 仅用于原个人功能回归测试，不能部署。原个人功能测试通过不代表它在 ywdj 开放；生产规则由 `tests/audit.test.ts` 独立验证。

## 7. 系统操作日志和备份

业务记录和系统审计分开。系统日志覆盖首次登记、追加、更正/作废、上传证据、移除草稿附件、导出、创建账号、账号字段变更及关键被拒绝操作。正式业务记录和对应成功日志原子提交。账号变更日志只记录字段和角色/状态变化，不记录密码、令牌或请求正文。

日志不是所有 HTTP 请求的全量访问日志，也不声称覆盖所有登录失败。管理员可查看并按目标编号查询。

网页 JSON 导出使用固定最大序号快照、遍历全部查询页，包含正式记录、附件元数据、URL 和摘要，**不包含原图片/PDF字节**。

`scripts/audit_backup.py` 另提供便携备份：正式记录 JSON、全部引用的原始附件、SHA-256 校验清单，以及权限允许时的系统日志。它不包含用户密码、全量账号设置、未提交草稿、旧个人笔记，不是整站 D1/R2 灾备，也不提供自动恢复。没有新增定时自动备份任务。

## 8. 后续扩展（本版未做）

告警 webhook 自动入库、审批式历史补录、部门/项目隔离、工单分派与通知、整改跟踪、全文索引优化、审计日志高级筛选、定时完整灾备和恢复演练。没有引入数据库权限治理、保留锁或区块链方案。
